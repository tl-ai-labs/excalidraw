## Conventions

- TypeScript strict throughout; formatting is Prettier 2 enforced through eslint-plugin-prettier (80 columns, double quotes, semicolons, trailing commas everywhere, 2-space indent); JSON files are Prettier-formatted with printWidth 256.
- Import order follows eslint import/order: builtin, external, @excalidraw/** packages after other externals, then parent, then sibling, and `import type` statements last; a blank line between groups; type-only imports are separate `import type { ... }` statements (consistent-type-imports).
- Files under packages/element/src import siblings relatively ("./bounds", "./types"); files under packages/excalidraw import runtime code from "@excalidraw/element" and "@excalidraw/common", element types from "@excalidraw/element/types", and never from the "@excalidraw/excalidraw" barrel.
- AGENTS.md: derived types use Merge<Base, Overrides> from @excalidraw/common/utility-types, never Omit<...> & {...}; DOM access in new code goes through app.ownerDocument / ownerWindow, never document or window globals.
- Scene elements are immutable: a change goes through newElementWith (or scene.mutateElement), which bumps version and versionNonce so history, collab and the render caches see it; a freshly created copy may be adjusted before it is returned.
- Render-path helpers (anything getArrowheadPoints, shape generation or getCanvasPadding calls) are constant-time and allocate nothing: no object, array or closure creation per call.
- No literal text in JSX: UI strings go through t("labels.<key>") with the English string in packages/excalidraw/locales/en.json only; other locale files are never edited.
- An element without arrowheadSize never gains the key: factories, restore and actions write the key only with a valid value, so existing snapshots stay byte-identical.
- Tests use vitest globals (describe, it, expect, vi) without importing them, as the existing tests do; jsdom tests render <Excalidraw handleKeyboardGlobally={true} /> in beforeEach, flush with `await act(async () => {})` in afterEach, and drive the editor through window.h, API, UI and Keyboard helpers.
- No test adds or rewrites a snapshot (no toMatchSnapshot / toMatchInlineSnapshot); assertions are explicit values, toBeCloseTo for floating point geometry.
- Comments are short, lowercase-start, explain why, and match the surrounding style; no TODO comments.

## Decisions

- Where the scale helpers live: getArrowheadSizeScale(element) and isArrowheadSize(value) are exported from packages/element/src/bounds.ts right after getArrowheadSize; they reach packages/excalidraw through the existing `export * from "./bounds"` in packages/element/src/index.ts, which is not edited. (not packages/element/src/arrowheads.ts (outside the write contract); not a new module (adds a file the requirement does not need)) — bounds.ts already owns getArrowheadSize, is in the allowlist, and is re-exported by the element index.
- Scale constants: packages/common/src/constants.ts exports ARROWHEAD_SIZE_SCALE: Readonly<Record<ArrowheadSize, number>> = { small: 0.5, medium: 1, large: 1.5 } and DEFAULT_ARROWHEAD_SIZE: ArrowheadSize = "medium"; every other file reads the scale only through getArrowheadSizeScale. (not literal scale numbers in bounds.ts or the action) — FR-2 asks for one source of truth next to the other style presets (STROKE_WIDTH, FONT_SIZES).
- Where the scale is applied: getArrowheadSize(arrowhead) keeps its signature and values; getArrowheadPoints computes size = getArrowheadSize(arrowhead) * getArrowheadSizeScale(element) before the short-segment fitting, and passes minSize / scale to getArrowheadAngle so a scaled head keeps the default head's opening angle; getArrowheadSizeBeyondLastSegment scales its arrow legible size and cardinality size by the same scale. (not adding an element parameter to getArrowheadSize (breaks callers without an element); not passing minSize unchanged to getArrowheadAngle (small arrow heads would open to 28 degrees)) — FR-3: the fitting still caps the head, callers without an element keep the base size, and medium/absent is bit-identical to today.
- Meaning of element bounds in FR-4 and AC-3: Head geometry: the points getArrowheadPoints returns and the head drawables shape.ts builds from them. getElementBounds of an arrow whose getArrowheadSizeScale is above 1 (large) also takes in its head drawables, so getCommonBounds (the PNG/SVG export frame), viewport culling and the hit-test bounding box contain large heads; absent, medium and small arrows keep today's shaft-only bounds. shape.ts needs no edit because every head shape already comes from getArrowheadPoints. (not adding heads to every arrow's bounds (moves existing bounds and export snapshots, violating NFR-2); not a head margin in scene/export.ts (outside the write contract, and culling and the hit-test bounding box would still cut large heads); not a fixed margin around large arrows (also grows the box along the shaft)) — Export frames are getCommonBounds plus a 10px padding: default heads (about 8.6px spread) and small ones fit inside it, large heads (about 12.8px plus stroke, a large circle about 12px) do not.
- binding.ts and index.ts: Neither file is edited: binding.ts only tests whether a head exists and never measures one, and index.ts already re-exports bounds.ts and renderElement.ts with export *. (not cosmetic edits to satisfy the in-scope list) — FR-5 and FR-8 are met without changing them.
- Panel control component and icons: RadioSelection<ArrowheadSize> with group "arrowhead-size", options small/medium/large using the existing FontSizeSmallIcon, FontSizeMediumIcon and FontSizeLargeIcon, testIds "arrowheadSize-small", "arrowheadSize-medium", "arrowheadSize-large"; icons.tsx is not edited. (not ButtonIconSelect (does not exist in this repo; RadioSelection is what actionChangeStrokeWidth uses); not new icons (S/M/L icons already exist)) — FR-11 asks for the stroke-width style of control, and FR-14 reuses icons when suitable.
- Which elements the action and the control target: isArrowheadSizeTarget(element), exported from actions/actionProperties.tsx: a linear element whose startArrowhead or endArrowhead is not null. The full styles panel (SelectedShapeActions in Actions.tsx) renders changeArrowheadSize right after changeArrowhead when targetElements.some(isArrowheadSizeTarget); the compact (CompactShapeActions) and mobile (MobileShapeActions) panels get it through actionChangeArrowProperties' PanelComponent, which renders it right after changeArrowhead under the same test on getTargetElements(getNonDeletedElements(elements), appState). (not predicates.arrowheads alone (true for an arrow tool with no selection and for arrows without heads); not leaving the compact and mobile panels without the control (a head can be picked there but not sized); not editing CombinedArrowProperties in Actions.tsx (both layouts already render changeArrowProperties, so one edit covers both)) — FR-12 and AC-4: on every layout the size control sits beside the arrowhead pickers for a selected arrow or line with a head, hidden for one without.
- Value the action writes and undo: perform writes the picked value as is (medium included) on each target, re-routes elbow arrows with updateElbowArrowRoute like changeArrowhead, returns no appState and captures IMMEDIATELY; undo of an absent-to-value change leaves arrowheadSize undefined, so tests assert toBeUndefined for that case. (not deleting the key when medium is picked (an extra branch with no visible difference); not a currentItemArrowheadSize AppState field (out of scope)) — FR-10 and NFR-3: the change rides the existing version bump and history deltas, with no AppState change.
- Paste styles for arrowheadSize: Applied when both the source and the pasted-onto element are linear, in a block placed just before the existing arrowheads block: a valid source value is set with newElementWith; an absent or invalid source value on a target that holds a value produces a forced copy (newElementWith(target, {}, true)) whose arrowheadSize key is then deleted; a target without the key is left untouched. (not newElementWith(target, { arrowheadSize: undefined }) (newElementWith ignores undefined updates, so a size-only change would not apply, and the key would linger); not clearing the size when the source is not linear (non-linear sources do not carry arrowhead styles)) — FR-13 and AC-8: the target matches the source, serializes without the key, bumps its version and is undoable.
- Restore of arrowheadSize: A restore.ts helper restoreArrowheadSize(element) deletes the key from the restoreElement working copy unless isArrowheadSize accepts its value; it runs at the top of the line/draw case and of the arrow case, before restoreElementWithProperties spreads the element. (not passing arrowheadSize through restoreElementWithProperties extra (the ...element spread would still carry an invalid value); not a separate ALLOWED_ARROWHEAD_SIZES set (duplicates ARROWHEAD_SIZE_SCALE)) — FR-9 and AC-2: valid kept, invalid dropped, absent stays absent.
- Canvas padding: getCanvasPadding becomes an exported function; for type arrow it returns Math.max(20, 40 * getArrowheadSizeScale(element)) when startArrowhead or endArrowhead is set, else 20; other types are unchanged. (not 40 * scale without the floor (small heads would get less padding than a headless arrow)) — FR-6 and AC-5: the start head counts, large heads get 60, default and headless arrows keep 40 and 20.
- Locale keys: labels.arrowheadSize = "Arrowhead size", labels.arrowheadSize_small = "Small", labels.arrowheadSize_medium = "Medium", labels.arrowheadSize_large = "Large", inserted after labels.arrowhead_cardinality_zero_or_many. (not reusing labels.small/medium/large (font-size strings that translators may word differently)) — FR-14: the control and its three options get their own English labels next to the other arrowhead strings.

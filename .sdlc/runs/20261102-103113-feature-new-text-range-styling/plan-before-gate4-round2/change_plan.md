# Change plan — 20261102-103113-feature-new-text-range-styling

Rendered by code from the accepted change spec (change-spec.json). Change the spec's section files and check them again; do not edit this file.

## Conventions

- TypeScript strict, ESM, Prettier via ESLint: 2 spaces, double quotes, trailing commas, 80 columns. `yarn test:code` runs with --max-warnings=0.
- Type imports are separate `import type` statements (consistent-type-imports). Keep import/order: external and @excalidraw/* first, then parent, then sibling, then type imports.
- Inside packages/element import siblings relatively (./textRanges). Inside packages/excalidraw import element code from "@excalidraw/element", types from "@excalidraw/element/types", and never through a packages/excalidraw barrel.
- New DOM use goes through app.ownerDocument / app.ownerWindow, or the ownerDocument of a mounted node. Never use the global document in new code.
- Prefer immutable data. Range arrays and range objects are never mutated in place: every change builds new objects (delta.ts compares entries by identity).
- A style-only change goes through newElementWith or a spread, never through mutateElement: mutateElement keeps the same object, so elementWithCanvasCache would paint stale text.
- New element fields get a JSDoc block in types.ts. Comments state why, not what, and stay short.
- Tests run on Vitest with globals, jsdom and vitest-canvas-mock. Use API, UI, Keyboard, getTextEditor, updateTextEditor and act from the existing helpers. Assert with expect; no toMatchSnapshot and no new snapshot files anywhere.
- In the test env getLineWidth returns text.length * 10, so x and width values in tests are exact multiples of 10.
- UI strings go through t("labels.x") and live in packages/excalidraw/locales/en.json only. Every other locale file is Crowdin's.

## Decisions

- Run constraint (Gate 0, answer 5): Run constraint: work only from this branch's code and the brief. Do not look at the upstream excalidraw repo, its PRs or issues, upstream/master or master, and do not base anything on them. This binds every phase and every model, the Gemini worker included. — The person's Gate 0 answer, word for word.
- Concurrent edits scope (Gate 0, answer 3): Concurrent edits: keep your reading of "survive" and do not narrow the brief to last-write-wins. The losing version's ranges are carried onto the winning text, no client shows stale offsets, all clients converge whichever order they receive versions in, and a removed range does not come back. (not Last-write-wins on the whole element or on the textRanges key) — The person's Gate 0 answer.
- Range data shape: ExcalidrawTextElement gets one optional key `textRanges?: ExcalidrawTextRanges` = { textHash: number; ranges: ExcalidrawTextRange[] }. textHash is hashString(originalText). A range is { id, start, end, z, color?, highlight?, retired?, origin? }: start and end are half-open UTF-16 offsets into originalText; id is randomId() and encodes no user, client or device; z is the layer; color and highlight are a colour string (sets it), null (clears it) or absent (leaves it alone). id, z, color and highlight never change after a range is created. (not Two top-level keys (ranges plus a tombstone list), which history would apply separately; not One range per attribute with a kind field: FR-1 says colour and/or highlight on one range) — One replaced value keeps text offsets and their hash together. Anchoring to originalText means a re-wrap alone never changes offsets (FR-1).
- Key absent by default (FR-2 as revised at Gate 1): An element that has NEVER had ranges carries no textRanges key, in memory or on save: newTextElement does not set it, restore never adds it, and a colour or reset that changes no visible style leaves it absent. An element whose ranges were all removed keeps its textRanges container as the marker FR-19 needs: clear, retired and collapsed records stay in it. — Keeps every existing snapshot and legacy file byte-identical, and gives a removal something to travel in.
- Layers: how one style is decided per character (FR-4): Ranges are layers, not disjoint segments. A style operation never rewrites an existing range's span: it adds one record on top with z = 1 + the highest z in the element. A colour pick adds { color } and touches nothing else, a highlight pick adds { highlight }, Reset adds { color: null, highlight: null }. A style with a null is a removal and also retires what it touches (see Removal and tombstones). For each attribute separately, the style of a character comes from the covering, non-retired record with that attribute present, ordered by highest z, then null before a string at equal z, then highest id. getTextStyleRuns is the only reader of this order and returns disjoint runs. Stored records of one attribute may overlap, because a style operation never shrinks a record. (not Disjoint records with no clear on top: two clients each removing half of a range would keep each other's remainder, so the whole range would come back; not Per-range revision counters: they cannot express a partial removal) — A grow-only set of immutable records is a join under union, which is what makes merging order-independent, and a partial removal survives because a clear is a record like any other.
- Text edit boundaries (FR-3): Text edits map offsets through diffText hunks. Insertion strictly inside a range extends it. Insertion exactly at a range's start shifts it and is not included. Insertion exactly at a range's end leaves it alone and is not included. A replacement overlapping a boundary leaves the inserted text outside the range. Deletion shrinks a range. A range whose characters are all deleted stays in the list collapsed (start === end) and native (no origin): it styles nothing from then on, and typing the same text again never reopens it, because mapStart(p) >= mapEnd(p) keeps a collapsed span collapsed. Its id is what stops a merge re-adding it from a peer's copy. (not Extending a range when typing at its end: it would also extend every clear, so typing after a removed word would change what was removed; not Dropping a range whose characters are all deleted: a peer then holds an id the base does not, so the merge re-adds it with the old text in origin, and retyping the word turns it red again) — One rule for start and one for end, used by the editor, list markers, history and carrying, so a range and a clear over it always move together.
- Merged element's version and nonce (FR-19, FR-20, NFR-3): reconcileElements picks the base exactly as today (shouldDiscardRemoteElement is unchanged and still exported). The merged element is { ...base, textRanges: merged }: inside reconcileElements it keeps the base's version, versionNonce, updated and every other field. Both clients call mergeTextRanges(base = the same winner, other = the same loser), so two clients with the same two versions compute the same element (NFR-3). If the merged ranges equal the base's, the base object itself is returned. In the app, Collab._reconcileElements then runs bumpElementVersions(reconciled, existing) (Collab.tsx:790, unchanged). After reconcile it fires in one case only: the client took a remote element at an equal version with a different nonce. That element gets version + 1, a fresh random versionNonce and a new updated, and nothing else holds that version and nonce. So after an equal-version race the client whose own element won holds the winner's version and nonce, the client that took the remote holds the bumped ones, and the two are equal in every other field, originalText and textRanges included. A higher-version winner is not bumped, so in that race both clients match on every field at once. Nothing rebroadcasts at that moment: Collab sets lastBroadcastedOrReceivedSceneVersion from the bumped total, so broadcastElements sees nothing newer. The next delivery ends the difference: the receiver takes the higher version, the merge returns it unchanged, no bump fires because the local version is lower, and both clients match on every field. mergeTextRanges also runs when version and nonce are equal, so a client still holding the un-merged winner picks up the merged ranges from a full sync. Two clients that both took the remote in one race hold the same version with different nonces and equal content: their next exchange is an ordinary equal-version race, one bumps once more, and the delivery after that ends it, as for every element today. (not Bumping the version inside the merge: two clients with the same two versions would compute different elements (NFR-3), and elements with no ranges must reconcile as today; not Deriving a new nonce from a hash of the merged state: the nonce is the tie-break, so it would change the winner) — Base fields are a last-write-wins register and the range table is a union, and the product of two joins is a join: commutative, associative and idempotent, so arrival order cannot matter. Collab's bump sits outside that join and behaves like one more local version with the same content, so it delays field-for-field equality by one delivery and cannot change what clients converge to.
- Carrying ranges onto the winning text (FR-19): Each record has a position register, a value compared as (higher version, then lower versionNonce). A record's register is its `origin` field if present, else { version, versionNonce, text: originalText, start, end } of the element holding it. If the base holds the id with no origin, the base's offsets win. Otherwise the newest register among the two sides is mapped onto the base's text through diffText(register.text, base.originalText, meter) and mapSpanThroughHunks, as the Diff budget decision states, and stored as the record's origin, unchanged. The mapping always starts from the register's own text, never from an intermediate merged text, so carrying through any number of merges gives the same offsets as carrying directly. A carried record whose characters are gone in the base stays in the list collapsed (start === end) with its origin, because a later winning text may still hold them. Any local edit (a style op or a text edit) makes every record native again by dropping origin. A bump never touches origin. A native record on a bumped element takes the bumped version and nonce as its register, with the same text and offsets, so it maps to the same place: two clients can hold different origin fields for a record until the next delivery, the newer register wins that delivery, and their offsets agree throughout. (not Common prefix and suffix only: when both ends of a text changed, everything in the middle would be lost; not Mapping from the previous merged text: path-dependent once three versions race; not Finding the styled substring by search: a word edited on the winning side would lose its range) — offsets = f(register, winning text) is a pure function of two joined values, which is the only way three-way races stay order-independent with no common ancestor.
- Removal and tombstones (FR-14, FR-19): A removal of a selection (Reset, or the transparent highlight swatch) does three things. It retires, by id, every record it touches all of whose string attributes it clears, whether it covers that record fully or partly, so no text path can bring any of that record back. For a record it covers only partly, it adds the part outside the selection as a fresh record at the same z (a kept part). It adds a clear record on top, which hides every lower layer over that span, stays in the list, and is carried like any other record. Two clients each clearing part of a range hide all of it, because each one's kept part lies under the other's clear. A colour edit racing a removal at the same z loses to the removal. A range created at a higher z by a client that had not seen the removal is a different range and stays. `retired: true` is the id tombstone: it is written by a removal and by undoing a style step, it is sticky under merge (logical OR), and a retired id is never revived. Undoing a removal and redoing a style step both re-add the style under a fresh id at its own z, so the layer order comes back as it was. retired records keep shifting with the text, because those re-adds read their offsets. (not A clear alone: the record stays alive on the peer's offsets, so a clear carried by a different diff path lands one character off at a repeated character and a sliver of the removed range shows; not Retiring only records the removal fully covers: a partly covered record stays alive on the peer's offsets, so the same sliver shows at its outer edge) — With no common ancestor, reconcile can only tell removal from not-yet-seen by a record that is present. A clear or a retired record is that record, and an id is the one thing a diff cannot misplace.
- Known limit: the remaining edge of a carried removal: A record a removal touched never shows again, whichever way a diff resolves a repeated character, because it is out by id. Exactly three things remain, and each needs a race. (1) The boundary between a clear and its kept part is placed by one diffText between the remover's text and the winning text. If the winning side changed a run of repeated characters or a repeated substring at that boundary, the kept part can sit to one side of where the keystrokes put it, or lose characters, by up to the amount of text the winning side added or removed there. (2) A clear hides a record its author had not seen, such as a colour made in the same race or another client's kept part, by position only. If that record and the clear reached the winning text by different paths, and the winning side changed repeated text at the clear's edge, that record can show beside the clear by the same amount. (3) If one client undoes a style step while another partly removes the same range, the kept part stays, because undo writes no clear. — The person asked at Gate 2 to close this or state it. Case 1 cannot be closed from text alone: repeated characters have no identity and reconcile sees no keystrokes. Cases 2 and 3 concern records the remover never saw, so they cannot be retired by id.
- Remote update dropped while editing (FR-21): While shouldDiscardRemoteElement drops a remote update because the local user edits that element (also while resizing or creating it), the update's text and every non-range field are discarded as today. Its ranges are NOT discarded: reconcileElements calls mergeTextRanges(local, remote), so each of its records, including clears and retired flags, joins the local element at once, mapped onto the local text, keeping the local version and nonce. The preview redraws from the scene update, and offsets address the text in the editor, so nothing is stale. Local records win position over remote for any id they hold natively. When editing ends nothing special runs: the local version is broadcast as usual if typing bumped it, and the next delivery of either version merges through the ordinary path to the same element on both clients, whichever wins on version. The discard branch never bumps, and a tie after editing ends takes Collab's bump as any equal-version race does. (not Holding the dropped update aside and replaying it at submit: it needs local state outside the element, which NFR-3 rules out of the merge; not Bumping the version at submit past the dropped update: it changes reconcile for no range reason and elements with no ranges must reconcile as today) — reconcileElements keeps its signature and stays pure, and FR-21's three demands are met by the same merge as FR-19.
- History (FR-9): textRanges is never written straight from a delta. ElementsDelta.applyDelta calls applyTextRangesDelta, which starts from the element's current records, shifts them to the delta's text if the delta holds originalText, then applies the difference between the delta's two sides by id: an id alive in the delta's deleted side and not in its inserted side is retired; an id alive in the inserted side and not in the deleted side is re-added, under a fresh id at its own z if its current record is retired. Offsets from a delta are used only when that delta also restores originalText and the element's current text equals the delta's deleted text, or when a record is collapsed on both the element and the delta's deleted side and the delta's inserted ranges address the resulting text, which is how undoing the step that lost a word brings its range back too. Undoing a range step after a remote text edit therefore keeps offsets on the current text. Undo and redo are forward operations: they merge with peers like any edit. (not Replacing textRanges from the delta: a peer's union would bring an undone record back, and offsets would go stale after an interleaved remote text edit) — Delta applies only the keys it holds, so a separate range key must be reconciled with the current text at apply time.
- Known limit: undo after a same-version merge: StoreSnapshot detects change by a rising version (store.ts:935), so a merge that keeps the version does not refresh the store snapshot. That is the client whose own element won, or who is editing, resizing or creating it, in reconcile's discard branch. A client that took the remote has a rising version, through the winner's higher version or Collab's bump, and its snapshot is current, so the limit does not reach it. On the discard-branch client, the next local edit's history step also spans records carried in by that merge. Undoing that one step retires those records, and a range a peer removed in that merge shows again, under a fresh id. Offsets stay valid and clients still converge. No workaround is written; packages/element/src/store.ts is outside the allowlist. — A merge must not raise a version inside reconcile (NFR-3). The limit needs a race the local element won, then a local edit, then an undo of that exact step.
- Known limit: overlap is not repaired at restore: Overlap between stored records is not malformed (FR-18). It stays as stored, in memory, in files and on the wire, and only getTextStyleRuns resolves it, by the fixed layer order. A saved element can therefore hold records that no character shows. — Overlap is the normal output of FR-4 and of merging. Flattening it would rewrite join state.
- Known limit: deleted text in origin.text: origin.text holds the losing version's full text, so after a concurrent-edit race text deleted on one client can stay in that element, in memory, in saves and on the wire, until the next style action or text edit on that element. Only a race writes it: a merge sets origin only when the base does not hold the id or holds it carried. A deletion with no race keeps the record collapsed and native, so it leaves no old text in the element on either client. — Carrying needs the register's own text, and any local edit drops it. This matches the PII line in requirements.md.
- Known limit: convergence waits for the next delivery: FR-19 holds once each client has received the other's latest version, not at the moment of a race. No client ever shows stale offsets meanwhile. Until then a bumped client differs from the other in version, versionNonce and updated, and if only one direction was delivered, the receiver holds merged records the sender lacks. Neither sends anything because of that. The next delivery is that client's next broadcast of any scene change, the full sync that follows a broadcast (SYNC_FULL_SCENE_INTERVAL_MS, 20 s, queued only by a broadcast), or a Firebase save by either client, which reconciles the stored scene back in. No timer forces one, so a quiet room stays in that state. Firebase: isSavedToFirebase compares the sum of versions, so a merge with no version rise does not make that client save. A client that took a remote element has a higher sum and saves, and saveToFirebase's own reconcileElements merges against the stored scene. So the stored scene lacks a merged record only if that client left before its throttled save ran, and then the winner's next version rise stores it. — excalidraw-app/** does not change, and these are today's delivery rules for every element.
- Known limit: native textarea undo: Ctrl+Z inside the textarea is the browser's own, because App's key handler bails inside a writable element. It changes text only, and FR-16 treats that as any other edit: a colour applied in the session is not undone by it, and a word it brings back stays unstyled, because that word's record stays collapsed. The app's undo after leaving the editor restores text and ranges together. — The textarea stays (FR-15), and its undo stack is not ours to change.
- Known limit: canvas bidi model and Arabic shaping: On a line with a visible run, layoutTextLine splits the line into ltr and rtl segments by a simple strong-character model, not the full Unicode bidi algorithm, so a mixed-direction line can place runs differently from the same unstyled line. Each canvas piece is its own fillText, so a run boundary inside an Arabic word breaks letter joining at that boundary. SVG text keeps one <text> per line, so the browser shapes and orders it, but SVG highlight rects use the same layout. Lines with no visible run take today's path. — The canvas has no API for shaping across fillText calls, and jsdom cannot test a fuller model.
- Known limit: the compact panel's Background title: The highlight picker has type elementBackground, and Picker.tsx titles its popup by type when showTitle is set, which ColorPicker does in compact mode. So in the compact and mobile panels the open popup reads "Background". The trigger's title and aria-label are right. Picker.tsx is outside the allowlist. — A cosmetic label in one mode, and the scope cannot change in this run.
- Known limit: the 1,024 record cap: MAX_TEXT_RANGES = 1024 records per element, counting retired, clear, collapsed and kept-part records. canonicalizeTextRanges keeps the highest (z, id), so past the cap the lowest layers are dropped, identically on every client, and that styling disappears. Records never leave the list otherwise, and a removal adds its clear plus up to two kept parts per touched record, so a heavily restyled element reaches the cap sooner than its visible runs suggest. A dropped record cannot return from a peer, because the merged list is cut the same way. — NFR-2 needs a bound on stored records, and a grow-only list has no other.
- Text diff mechanism (FR-3, FR-16, FR-19, NFR-2, NFR-3, Gate 4): diffText no longer fills a table and no longer falls back at a cell cap; MAX_DIFF_CELLS is gone. Everything is in packages/element/src/textDiff.ts, which changes this round, and diffText stays the one function shiftTextRanges and mergeTextRanges share. It searches before it trims. A queue of gaps starts with the two whole texts. Each gap takes its longest common run of at least MIN_MATCH_LENGTH (3) characters, which splits it into a left and a right gap, breadth-first. An index of oldText's 3-character grams finds the runs: a flat Int32Array table sized to the text, not a Map. In a gap the search starts at the middle of the gap's new text and moves outward, so that of runs of equal length the one nearest the middle wins and a repetitive note splits in half each time. It steps by the best length so far minus 1, because a longer run must hold a whole gram at one of those positions. At each position it tries at most MAX_MATCH_CANDIDATES (16) old positions, nearest the gap's own diagonal first. The longer of the common prefix and common suffix is the first gap's starting best, so a run must be strictly longer to beat it: a tie stays where trimming put it, and a change that repeats text beside it behaves as before. When the search ends, only the first and last gaps are trimmed of a common prefix and suffix, which keeps short matches at the text's two ends as before. A change of fewer than MIN_MATCH_LENGTH characters in total skips the search, so typing one character costs only the trim and gives the hunk it gave before. A block never starts or ends inside a surrogate pair. Every step charges a DiffMeter, and when the meter runs out the search stops and keeps what it has found (see Diff budget per merge). Repeated text has no identity: when two copies of a run are equally long, a range follows the one this search reaches first, and only the person typing knows which copy they meant. (not Raising the cell cap: the second cause is under the cap, and the digits case fails at exactly 1,000,000 cells with 2 hunks; not Myers or any other minimal edit script: a minimal script still matches the original's letters inside added text, so runs fragment and the anchor is lost; not Tokenising into words first: generated text has no words, and the brief needs both; not Anchoring only on grams unique to both texts: repeated lines and repeated paragraphs have none; not Scanning each gap left to right: on tied runs it peels one block per pass, and Tab on 100 identical lines ran out of budget and lost 316 of 400 words; not Sliding only the first and last hunks after a trim: a word of two letters left after the trim cannot anchor, so "Bid" to "Before Bid after" still loses the word; not A Map as the gram index: at a budget of 2.5M units the forged element took 65 ms per reconcile, against about 26 ms for the flat table at 2M) — There are three causes, not two, and this covers all of them. First, the cap fell back to one hunk with about 1,000 characters between the first and last change. Second, the eager backtrack matched the original's letters inside added text, the runs fragmented, and MIN_MATCH_LENGTH dropped them. Third, found while proving this: the trim ran first, so "Before ..." added in front of "Bid" took its "B" and the insertion landed inside the word, which is why "Bid" widened over the added text and why "Bid" to "Bold Bid" widened too. Measured with a scratch copy under node, never on a project file, and through the real editor in jsdom by redirecting the module in a scratch config. A word changed at each end at 1,010, 1,100 and 1,500 characters keeps every word (162 of 162, 177 of 177, 243 of 243). Tab on all lines of 468, 1,054 and 1,407 characters and Shift+Tab on 1,126 and 1,503 characters keep the word at its true offset, on prose and on digits, in the real editor. 100 and 330 characters on each side of the label keep all 4 words; 330 on each side of the 326-character paragraph keeps all 53. mapTextSpan(digits.slice(5000, 5100), digits, 10, 20) is { start: 5010, end: 5020 }. Scripted random edits, words untouched by an edit that land exactly, old diff against this one: prose at 800 characters with 12 edits 98.92% to 99.88%, at 3,000 with 10 edits 19.24% to 99.98%, at 10,000 with 200 edits 0.80% to 99.89%; generated text at 3,000 with 10 edits 20.82% to 100%, at 10,000 with 200 edits 1.26% to 99.96%. 4,000 fuzzed cases, half with emoji: hunks always rebuild the new text, and no hunk edge falls inside a surrogate pair. The work is a pure function of the two texts and the meter, and uses no clock, randomness or module state (NFR-3). Tab on all lines of a 100,000-character note used 1.81M work units, about 11 ms; Tab on 1,000 identical lines used 1.68M, about 7 ms.
- Diff budget per merge (NFR-2, Gate 3): mergeTextRanges bounds its diff work per call with one work meter, which replaces the cell budget. textDiff.ts holds the only constant, MAX_DIFF_WORK, and textRangeMerge.ts repeats none of it: MAX_MERGE_DIFF_CELLS, DIFF_TEXT_MAX_CELLS and getCoarseHunk are removed, so the two files cannot disagree. Imports: `import { MAX_DIFF_WORK, diffText, mapSpanThroughHunks } from "./textDiff";` and `import type { DiffMeter, TextHunk } from "./textDiff";`. Order, unchanged from Gate 3: after allIds, `const survivors = canonicalizeTextRanges([...allIds].map((id) => (baseMap.get(id) ?? otherMap.get(id))!)).reverse();` and the loop is `for (const { id } of survivors)`, so records the MAX_TEXT_RANGES cap drops are gone before any diff runs, and the highest (z, id) is served first. Spend: before the loop, `const meter: DiffMeter = { left: MAX_DIFF_WORK };` and `const hunksByText = new Map<string, readonly TextHunk[]>();`. On a miss in hunksByText, `hunks = diffText(reg.text, base.originalText, meter);` and the result is stored under reg.text, so each distinct text is paid for once. diffText charges the meter for what it does and stops when the meter runs out. A text it cannot pay to index costs nothing, so it does not stop a later, shorter one. `const mapped = mapSpanThroughHunks(hunks, reg.start, reg.end);` follows as before. Test, in packages/excalidraw/tests/data/reconcile.textRanges.test.ts, counts work and never times it: `vi.mock("@excalidraw/element/textDiff", ...)` wraps diffText in a vi.fn over importOriginal, cleared just before the merge, so its calls and results are visible. W is 10,000 generated characters. The winner holds 1,024 carried records with distinct 100-character origins, L1 holds one record at a higher z whose origin is W.slice(5000, 5100) with offsets [10, 20), and L2 holds three records at a lower z whose ids sort first, with distinct 100-character origins. One merge makes exactly 1,024 diffText calls, the first on W.slice(5000, 5100) and none on an L2 origin. More than none and fewer than 1,024 of them return several hunks, and the last returns one, which shows the budget ran out. That record lands at [5010, 5020) in both arrival orders, both orders give the same element, merging L2 again returns the base object, and the lowest surviving record is collapsed with its origin kept. A second case carries a range across a change at each end of W to its true offsets. (not Iterating all ids in sorted order: which records the cap has already dropped depends on arrival order, so a doomed record would spend budget on one client and not on another, and those clients would stop converging; not Pricing a diff before it runs, by trimmed cells: the work no longer follows cells, and a text could only be served whole or not at all; not A separate merge constant: a second number is the disagreement this round removes; not A fixed price per text: a one-word edit would cost as much as a hostile text, and a fourth ordinary register would lose its diff) — Value: 2,000,000 work units for one merge, the same as for one local diff. Stated worst case, pure, whatever the input: one merge spends at most MAX_DIFF_WORK + 2 * min(old length, new length) + 2 units, because a run in progress finishes before the meter is read, and at most 4 * old length + new length of that is the index, which runs only if the meter can pay for it. Outside the meter are the trim, at most 2 * min(old length, new length) compares per distinct register text, so linear in the payload as before, and sorting the blocks found, each of which cost at least 4 units. Measured on 115 adversarial inputs (random text over small alphabets, periodic text, blocks of 3 characters, no match at all), with old texts up to 400,000 characters: the slowest took 28.6 ms (25,000 blocks of 3 characters), and the largest overrun past zero was 102,169 units. The 255 KB forged element, 1,024 records with distinct 100-character origins against a 10,000-character text, takes 23 to 33 ms per reconcile, about 26 ms once warm, against 17 to 23 ms on the code before this round and 4.4 to 4.5 s before Gate 3; the meter serves 57 of its 1,024 diffs. An ordinary race stays far under the budget: three register texts of 10,000 characters use about 210,000 units. Convergence: a record native to the base and a register equal to the base are not mapped and cost nothing. Every other surviving record is remapped from its own register on every merge that reaches the loop, and a merge whose other side has no records returns the base and adds none. So nothing carries spend between calls: it depends only on the base text and the registers of the surviving records, not on how a client reached them. The survivors are the same on every client, because the top MAX_TEXT_RANGES by (z, id) of a union does not depend on the order of the unions, and the cut comes before any diff. The order they are served in comes from that same canonical sort, and a partial diff is a pure function of the two texts and what the meter holds on arrival, so the result is the same however a client reached those survivors. A bumped client's native records register the base's own text, which diffText answers with no work, so a bump changes no spend. Two clients with the same two versions compute the same element (NFR-3), and the merge stays idempotent: a repeat sees the same survivors and registers, gets the same hunks and returns the base. meter and hunksByText live and die in one call, so no local-only state enters the merge.
- Known limit: the diff budget is per element: MAX_DIFF_WORK is per diffText call for a local text edit and per element for a merge, one mergeTextRanges call, so many forged elements still add up in proportion to payload size. What really happens past the budget: a diff that cannot pay for its index returns one hunk, the text between the common prefix and the common suffix, and a diff that runs out partway keeps every block it has found and leaves each remaining gap as a hunk.

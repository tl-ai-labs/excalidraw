## Conventions

- TypeScript strict, ESM, Prettier via ESLint: 2 spaces, double quotes, trailing commas, 80 columns. `yarn test:code` runs with --max-warnings=0.
- Type imports are separate `import type` statements (consistent-type-imports). Keep import/order: external and @excalidraw/* first, then parent, then sibling, then type imports.
- Inside packages/element import siblings relatively (./textRanges). Inside packages/excalidraw import element code from "@excalidraw/element", types from "@excalidraw/element/types", and never through a packages/excalidraw barrel.
- New DOM use goes through app.ownerDocument / app.ownerWindow, or the ownerDocument of a mounted node. Never use the global document in new code.
- Prefer immutable data. Range arrays and range objects are never mutated in place: every change builds new objects (delta.ts compares entries by identity).
- A style-only change goes through newElementWith or a spread, never through mutateElement: mutateElement keeps the same object, so elementWithCanvasCache would paint stale text.
- New element fields get a JSDoc block in types.ts. Comments state why, not what, and stay short.
- Tests run on Vitest with globals, jsdom and vitest-canvas-mock. Use API, UI, Keyboard, getTextEditor, updateTextEditor and act from the existing helpers. Assert with expect; no toMatchSnapshot and no new snapshot files anywhere.

- UI strings go through t("labels.x") and live in packages/excalidraw/locales/en.json only. Every other locale file is Crowdin's.

## Decisions

- Run constraint (Gate 0, answer 5): Run constraint: work only from this branch's code and the brief. Do not look at the upstream excalidraw repo, its PRs or issues, upstream/master or master, and do not base anything on them. This binds every phase and every model, the Gemini worker included. — The person's Gate 0 answer, word for word.
- Concurrent edits scope (Gate 0, answer 3): Concurrent edits: keep your reading of "survive" and do not narrow the brief to last-write-wins. The losing version's ranges are carried onto the winning text, no client shows stale offsets, all clients converge whichever order they receive versions in, and a removed range does not come back. (not Last-write-wins on the whole element or on the textRanges key) — The person's Gate 0 answer.
- Range data shape: ExcalidrawTextElement gets one optional key `textRanges?: ExcalidrawTextRanges` = { textHash: number; ranges: ExcalidrawTextRange[] }. textHash is hashString(originalText). A range is { id, start, end, z, color?, highlight?, retired?, origin? }: start and end are half-open UTF-16 offsets into originalText; id is randomId() and encodes no user, client or device; z is the layer; color and highlight are a colour string (sets it), null (clears it) or absent (leaves it alone). id, z, color and highlight never change after a range is created. (not Two top-level keys (ranges plus a tombstone list), which history would apply separately; not One range per attribute with a kind field: FR-1 says colour and/or highlight on one range) — One replaced value keeps text offsets and their hash together. Anchoring to originalText means a re-wrap alone never changes offsets (FR-1).
- Key absent by default (FR-2 as revised at Gate 1): An element that has NEVER had ranges carries no textRanges key, in memory or on save: newTextElement does not set it, restore never adds it, and a colour or reset that changes no visible style leaves it absent. An element whose ranges were all removed keeps its textRanges container as the marker FR-19 needs: clear records and retired records stay in it, and the ranges array may be empty. — Keeps every existing snapshot and legacy file byte-identical, and gives a removal something to travel in.
- Layers: how one style is decided per character (FR-4): Ranges are layers, not disjoint segments. A style operation never rewrites an existing range: it adds one record on top with z = 1 + the highest z in the element. A colour pick adds { color }, a highlight pick adds { highlight }, Reset adds { color: null, highlight: null }. For each attribute separately, the style of a character comes from the covering, non-retired record with that attribute present, ordered by highest z, then null before a string at equal z, then highest id. getTextStyleRuns is the only reader of this order and returns disjoint runs; splitting a range is what those runs show, not what is stored. Stored records of one attribute may overlap, because a record never shrinks. (not Disjoint records that are split on every edit: two clients each removing half of a range would keep each other's remainder, so the whole range would come back; not Per-range revision counters: they cannot express a partial removal) — A grow-only set of immutable records is a join under union, which is what makes merging order-independent, and a partial removal survives because a clear is a record like any other.
- Text edit boundaries (FR-3): Text edits map offsets through diffText hunks. Insertion strictly inside a range extends it. Insertion exactly at a range's start shifts it and is not included. Insertion exactly at a range's end leaves it alone and is not included. A replacement overlapping a boundary leaves the inserted text outside the range. Deletion shrinks a range. A non-retired range whose characters are all deleted is removed from the list. (not Extending a range when typing at its end: it would also extend every clear, so typing after a removed word would change what was removed) — One rule for start and one for end, used by the editor, list markers, history and carrying, so a range and a clear over it always move together.
- Merged element's version and nonce (FR-19, FR-20, NFR-3): reconcileElements picks the base exactly as today (shouldDiscardRemoteElement is unchanged and still exported). The merged element is { ...base, textRanges: merged }: it keeps the base's version, versionNonce, updated and every other field, and no version is bumped. Both clients call mergeTextRanges(base = the same winner, other = the same loser) and compute the same bytes. If the merged ranges equal the base's, the base object itself is returned, so nothing churns. Since no version rises, Collab's scene-version check sees nothing to send and Portal does not rebroadcast. A later delivery of either version, including Collab's periodic full sync, merges to the same result because the merge is idempotent. mergeTextRanges also runs when version and nonce are equal, so a client still holding the un-merged winner picks up the merged ranges from a full sync. (not Bumping the version on merge: not associative, three clients would disagree and each bump rebroadcasts; not Deriving a new nonce from a hash of the merged state: the nonce is the tie-break, so it would change the winner) — Base fields are a last-write-wins register and the range table is a union, and the product of two joins is a join: commutative, associative and idempotent, so arrival order cannot matter.
- Carrying ranges onto the winning text (FR-19): Each record has a position register, a value compared as (higher version, then lower versionNonce). A record's register is its `origin` field if present, else { version, versionNonce, text: originalText, start, end } of the element holding it. If the base holds the id with no origin, the base's offsets win. Otherwise the newest register among the two sides is mapped onto the base's text with mapTextSpan(register.text, base.originalText, register.start, register.end) and stored as the record's origin, unchanged. The mapping always starts from the register's own text, never from an intermediate merged text, so carrying through any number of merges gives the same offsets as carrying directly. A carried record whose characters are gone in the base stays in the list collapsed (start === end) with its origin, because a later winning text may still hold them. Any local edit (a style op or a text edit) makes every record native again by dropping origin. (not Common prefix and suffix only: when both ends of a text changed, everything in the middle would be lost; not Mapping from the previous merged text: path-dependent once three versions race; not Finding the styled substring by search: a word edited on the winning side would lose its range) — offsets = f(register, winning text) is a pure function of two joined values, which is the only way three-way races stay order-independent with no common ancestor.
- Removal and tombstones (FR-14, FR-19): A removal of a selection is a clear record on top. It hides every lower layer over that span, stays in the list, and is carried like any other record, so the removed characters stay unstyled on every client in every arrival order, and two clients each clearing part of a range hide all of it. A colour edit racing a removal at the same z loses to the removal. A range created at a higher z by a client that had not seen the removal is a different range and stays. `retired: true` is the id tombstone: it is written only by undoing a style step, it is sticky under merge (logical OR), and a retired id is never revived; redo re-adds the style under a fresh id. retired records keep shifting with the text, because redo reads their offsets. — With no common ancestor, reconcile can only tell removal from not-yet-seen by a record that is present. A clear or a retired record is that record.
- Remote update dropped while editing (FR-21): While shouldDiscardRemoteElement drops a remote update because the local user edits that element (also while resizing or creating it), the update's text and every non-range field are discarded as today. Its ranges are NOT discarded: reconcileElements calls mergeTextRanges(local, remote), so each of its records, including clears and retired flags, joins the local element at once, mapped onto the local text, keeping the local version and nonce. The preview redraws from the scene update, and offsets address the text in the editor, so nothing is stale. Local records win position over remote for any id they hold natively. When editing ends nothing special runs: the local version is broadcast as usual if typing bumped it, and the next delivery of either version merges through the ordinary path to the same element on both clients, whichever wins on version. (not Holding the dropped update aside and replaying it at submit: it needs local state outside the element, which NFR-3 rules out of the merge; not Bumping the version at submit past the dropped update: it changes reconcile for no range reason and elements with no ranges must reconcile as today) — reconcileElements keeps its signature and stays pure, and FR-21's three demands are met by the same merge as FR-19.
- History (FR-9): textRanges is never written straight from a delta. ElementsDelta.applyDelta calls applyTextRangesDelta, which starts from the element's current records, shifts them to the delta's text if the delta holds originalText, then applies the difference between the delta's two sides by id: an id alive in the delta's deleted side and not in its inserted side is retired; an id alive in the inserted side and not in the deleted side is re-added, under a fresh id if its current record is retired. Offsets from a delta are used only when that delta also restores originalText and the element's current text equals the delta's deleted text. Undoing a range step after a remote text edit therefore keeps offsets on the current text. Undo and redo are forward operations: they merge with peers like any edit. (not Replacing textRanges from the delta: a peer's union would bring an undone record back, and offsets would go stale after an interleaved remote text edit) — Delta applies only the keys it holds, so a separate range key must be reconciled with the current text at apply time.
- Known limit: undo after a same-version merge: StoreSnapshot detects change by a rising version, so a merge that keeps the version does not refresh the store snapshot. The next local edit's history step therefore also spans records carried in by that merge, and undoing that one step retires them. Offsets stay valid and clients still converge. No workaround is written; packages/element/src/store.ts is outside the allowlist. — Keeping version and nonce stable is what stops the rebroadcast loop. The limit needs a race, then a local edit, then an undo of that exact step.
- Restore and malformed input (FR-18, NFR-2): sanitizeTextRanges(raw, originalText) is the single validator. restore.ts calls it, and every reader (getTextStyleRuns, the merge, the delta) calls it too, so bad data from any path is repaired or dropped and never thrown on. It drops the whole container when textHash does not match originalText (stale against the text, for example an older client edited the text). It drops any record with wrong types, an inverted span, or no usable attribute; removes an unusable colour attribute; clamps out-of-bounds offsets; and caps the list at MAX_TEXT_RANGES by keeping the highest (z, id). Valid input comes back as the same object. Overlap is not dropped at restore, because stored overlap is the normal output of FR-4 and of a merge and repairing it there would break merging: an overlap is resolved by the fixed layer order, so the renderer only ever receives disjoint runs. (not Flattening overlap in restore: restoreElements runs on every remote element before reconcile, so it would rewrite join state and make merging path-dependent) — Validate at restore and render defensively, with one function for both.
- Colours are untrusted (NFR-2): A range colour is valid when it is a string of at most 64 characters and colorToHex(value) is not null. Colours reach SVG through setAttribute and the preview through element.style only, never through markup strings. Applying a transparent colour is stored as null, so a user cannot make text invisible through a range. Colours get applyDarkModeFilter(value, isDark) on canvas, in SVG and in the preview, as strokeColor does. — One rule shared by restore, renderers and the actions.
- No selection and not editing (FR-13): With an empty selection, or with the element selected and not being edited, actionChangeStrokeColor behaves exactly as today: it sets strokeColor and ranges keep their own colour. The range path runs only when appState.editingTextElement is set and the textarea has a non-empty selection. — The reading the person accepted at Gate 1.
- Removing a style: the control (FR-14): A new button labelled "Reset text color and highlight" (action resetTextStyle, eraser icon) shows in the styles panel beside the text highlight picker while a text element is edited. Clicking it returns the selected characters to the element's own colour and to no highlight. With an empty selection it does nothing. Choosing the transparent swatch in the highlight picker also removes only the highlight. Both count as removal for FR-19. (not A No color swatch in the stroke picker: the stroke palette has no such entry and picking transparent is a colour for every other element; not Picking the element's strokeColor by hand: the range would keep that colour after a later strokeColor change) — One visible control does both jobs of FR-14, and the stroke picker keeps its meaning.
- Highlight control (FR-12): A new action changeTextHighlight renders a ColorPicker while a text element is edited, with type "elementBackground" for the background palette and a new optional prop popup="textHighlight" naming its popup. It needs no new ColorPickerType, because colorPickerUtils.ts is outside the allowlist, and `popup` lets it sit beside the background picker while a sticky note label is edited. With an empty selection it changes nothing. — Two pickers sharing one openPopup value would open together.
- Editor and preview (FR-10, FR-15, FR-16): The <textarea> stays. Its selectionStart and selectionEnd are originalText offsets as they are, because editable.value is originalText. While the element has visible runs, a preview layer (class excalidraw-wysiwyg-preview) sits directly behind the textarea with the same box, font and wrapping, shows the full text with coloured and highlighted spans, and the textarea's own text is transparent with its caret in the element's colour. With no visible runs there is no preview node and the textarea styles are as today. The canvas paints the styling when editing ends, because the canvas skips the element being edited. (not A contenteditable editor: out of scope for this run) — The After line needs the word to show in red while editing, and jsdom can drive a textarea.
- Rendering (FR-5, FR-6, FR-17, NFR-1): Renderers call getTextLineRuns(element), which aligns element.text with originalText without measuring. When it returns null the renderer's existing code runs untouched, so elements with no ranges paint and export byte-identically. Canvas: all highlights first as fillRect, then text as one fillText per piece with textAlign left at an explicit x. SVG: a highlight is a <rect> appended to the element's <g> before every <text>; a coloured run is a <tspan> with fill; a run with no colour is a plain text node; each line stays one <text> with today's attributes, so text-anchor and the browser's bidi still apply. A highlight rect spans the full line height. Range colour and highlight are paint-only and never reach measureText. — A <tspan> carries a fill but no background, which Gate 0 accepted as a rect behind the text.

Verification uses yarn test:typecheck, yarn test:code and yarn test:app --watch=false as three separate commands. Never yarn test:update, which rewrites snapshots and would hide a regression. No existing snapshot file changes (AC-13). — Run decisions from the brief and Gate 0, answer 2.

### U02 — create `packages/element/src/textDiff.ts` (codegen)

Behaviour: Pure diff between two strings as hunks, and mapping of a range's start and end through those hunks.

Rules:
1. Exact constants: MIN_MATCH_LENGTH = 3, MAX_DIFF_CELLS = 1_000_000. No clock, no randomness, no module state.
2. diffText step 1: if oldText === newText return [].
3. diffText step 2: prefix = length of the common leading code units. If prefix > 0 and oldText.charCodeAt(prefix - 1) is a high surrogate (0xD800 to 0xDBFF), subtract 1.
4. diffText step 3: suffix = length of the common trailing code units, never more than Math.min(oldText.length, newText.length) - prefix. If suffix > 0 and oldText.charCodeAt(oldText.length - suffix) is a low surrogate (0xDC00 to 0xDFFF), subtract 1.
5. diffText step 4: a = oldText.slice(prefix, oldText.length - suffix), b = newText.slice(prefix, newText.length - suffix), n = a.length, m = b.length. If n === 0, or m === 0, or n * m > MAX_DIFF_CELLS, return one hunk { oldStart: prefix, oldEnd: prefix + n, newStart: prefix, newEnd: prefix + m }.
6. diffText step 5: fill a Uint16Array of (n + 1) * (m + 1) cells where cell (i, j) is the longest common subsequence length of a.slice(i) and b.slice(j), computed from i = n - 1 and j = m - 1 downwards: if a[i] === b[j] then cell(i, j) = 1 + cell(i + 1, j + 1), else Math.max(cell(i + 1, j), cell(i, j + 1)).
7. diffText step 6: walk i = 0, j = 0 while i < n and j < m. If a[i] === b[j], record the pair (i, j) and advance both. Otherwise, if cell(i + 1, j) >= cell(i, j + 1) advance i, else advance j.
8. diffText step 7: group pairs into blocks: a block is a maximal run where i and j both rise by 1. Drop every block shorter than MIN_MATCH_LENGTH.
9. diffText step 8: walk kept blocks with cursors ai = 0, bi = 0. Before each block, if ai < block's i start or bi < block's j start, push a hunk spanning the gap with prefix added to all four numbers, then move ai and bi past the block. After the last block, if ai < n or bi < m push the final hunk. With no kept blocks this is one hunk for the whole middle. Hunks are ascending and never touch.
10. mapSpanThroughHunks: nextStart = mapStart(start), nextEnd = mapEnd(end), and return { start: nextStart, end: Math.max(nextStart, nextEnd) }.
11. mapStart(p): delta = 0; for each hunk in order: if p < hunk.oldStart stop; if p <= hunk.oldEnd return hunk.newEnd; delta = hunk.newEnd - hunk.oldEnd. Return p + delta. So an insertion exactly at a range's start moves the start past the inserted text.
12. mapEnd(p): delta = 0; for each hunk in order: if p <= hunk.oldStart stop; if p <= hunk.oldEnd return hunk.newStart; delta = hunk.newEnd - hunk.oldEnd. Return p + delta. So an insertion exactly at a range's end leaves the end where it is.
13. mapTextSpan: mapSpanThroughHunks(diffText(oldText, newText), start, end).

Exports:
- `type TextHunk(): { oldStart: number; oldEnd: number; newStart: number; newEnd: number }`
- `function diffText(oldText: string, newText: string): TextHunk[]`
- `function mapSpanThroughHunks(hunks: readonly TextHunk[], start: number, end: number): { start: number; end: number }`
- `function mapTextSpan(oldText: string, newText: string, start: number, end: number): { start: number; end: number }`

Import line: `import { diffText, mapSpanThroughHunks, mapTextSpan } from "./textDiff";`

Style from: `packages/element/src/textMeasurements.ts:1-32` — Shape of a small pure text module in this package.

Covers: FR-3, FR-19

Checks: lint

### U03 — create `packages/element/src/textRanges.ts` (codegen)

Behaviour: The range model: validation, resolving layers to disjoint style runs, local style and text operations.

Rules:
1. Imports: colorToHex, isTransparent, randomId from @excalidraw/common; hashString from "." (as textElement.ts imports from "."); diffText, mapSpanThroughHunks from ./textDiff; types from ./types. Exact constants: MAX_TEXT_RANGES = 1024 (exported), MAX_TEXT_RANGE_ID_LENGTH = 64, MAX_TEXT_RANGE_COLOR_LENGTH = 64.
2. isValidTextRangeColor: typeof value === "string", value.length <= 64, and colorToHex(value) !== null.
3. canonicalizeTextRanges: return a new array sorted by z ascending, then id ascending, comparing ids with < and > (never localeCompare). If longer than MAX_TEXT_RANGES keep only the last MAX_TEXT_RANGES entries.
4. Every record is written with keys in the order id, start, end, z, color, highlight, retired, origin, and with absent keys left out, not set to undefined.
5. areTextRangesEqual: both undefined is true, exactly one undefined is false, otherwise textHash equal, ranges lengths equal, and each index equal on id, start, end, z, color, highlight, retired and on every field of origin.
6. sanitizeTextRanges step 1: return undefined unless raw is an object with an array `ranges`. Return undefined if raw.textHash !== hashString(originalText). Read only the first MAX_TEXT_RANGES * 16 entries of ranges. Never throw.
7. sanitizeTextRanges step 2, per entry, dropping it if any check fails: it is a non-null object; id is a string of length 1 to 64 not already seen; start, end and z are integers (Number.isInteger); z >= 0; end >= start.
8. sanitizeTextRanges step 3: keep color only if it is null or isValidTextRangeColor, the same for highlight. Drop the entry if neither key remains.
9. sanitizeTextRanges step 4: clamp start and end to 0..originalText.length. Keep retired only when it is exactly true. Keep origin only when it is an object whose version and versionNonce are integers, whose text is a string, and whose start and end are integers with 0 <= start <= end <= text.length; otherwise leave it out.
10. sanitizeTextRanges step 5: drop the entry if start === end and it has neither retired nor origin. Then canonicalizeTextRanges. Return undefined if nothing remains. If the result equals raw (areTextRangesEqual) return raw itself, else return { textHash: raw.textHash, ranges }.
